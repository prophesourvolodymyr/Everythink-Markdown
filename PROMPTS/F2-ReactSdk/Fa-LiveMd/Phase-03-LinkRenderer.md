# Phase 03 of Fa3-LinkRenderer — Wiki-Link & Semantic Link Rendering

## Context

Phase 01 (Fa1-SyntaxHider) and Phase 02 (Fa2-TextStyler) are complete. The `@everthink/react-emd` package at `sdk/react-emd/` now has two decoration builders registered in `view-plugin.ts`'s `BUILDERS` array. Fa1 hides syntax markers (`#`, `**`, `*`, backticks, brackets, `>`, `-`, `[ ]`). Fa2 applies visual styles: headings→size+weight, StrongEmphasis→bold, Emphasis→italic, InlineCode→monospace+bg, Blockquote→left border, Link→underline+accent, HorizontalRule→hidden.

The ViewPlugin skeleton (`view-plugin.ts`) has a debounced decoration rebuild cycle and calls builders sequentially via the BUILDERS array. 32 tests pass (12 syntax-hider + 13 text-styler + 7 view-plugin). `npm run build` produces `dist/index.js`, `dist/editor.js`, `dist/viewer.js`.

Standard markdown links (`[text](url)`) are already styled by Fa2-TextStyler with `color: var(--emd-accent)` and `text-decoration: underline`. Fa3-LinkRenderer now needs to handle the two EMD-specific link types that Fa2 doesn't know about: **wiki-links** (`[[target]]`) and **semantic links** (`→ relation: target`).

## Codebase learnings (from Phase 01 and 02)

**Package structure:** `sdk/react-emd/` is a Vite library-mode package. Source in `src/`, tests in `__tests__/`. Path alias `@live-md/*` → `src/live-md/*`.

**Test approach:** Tests create real `EditorState` with `markdown({ base: markdownLanguage })`, get `syntaxTree(state)`, call the builder, assert on returned decorations. Access decoration attributes via `(decoration as any).spec?.attributes?.style`.

**Lezer markdown nodes** (verified empirically):
- `Link` — container for `[text](url)`. Contains `LinkMark`, `URL` children.
- `URL` — the `(url)` part within a Link.
- `Image` — container for `![alt](url)`.
- `FencedCode`, `HTMLBlock` — containers whose descendants are skipped.

**Wiki-links in lezer:** The standard `@codemirror/lang-markdown` parser does NOT have a built-in wiki-link node type. Wiki-links (`[[target]]`) are parsed as plain text. To handle them, Fa3 must either:
- Register a custom lezer grammar extension that adds wiki-link node types, OR
- Post-process decorations by finding `[[...]]` patterns in the raw document text between the decorations already generated by other builders.

**Recommended approach for Phase 03:** Use regex scanning on the document text to find `[[...]]` and `→ ...` patterns, verify they fall in regions not covered by FencedCode/HTMLBlock (use the existing syntax tree to check), and create decorations for them. This avoids the complexity of custom lezer grammar extensions and is appropriate for Phase 03.

**Semantic links:** The `→ relation: target` syntax uses the Unicode arrow `→` (U+2192). These are parsed as plain text by lezer. There is no special node type for semantic links in standard markdown.

**Decoration types:**
- `Decoration.mark({ attributes: { style: '...', class: '...' } })` — applies CSS to a text range. Already used by Fa2.
- `Decoration.replace({})` — hides a text range. Used by Fa1.
- `Decoration.widget({ widget })` — replaces a range with a DOM element. Will be used by Fa3 for semantic link badges.
- `Decoration.set.of(ranges, true)` — creates sorted DecorationSet.

## What to build

### 1. LinkRendererConfig

Add to `sdk/react-emd/src/live-md/types.ts`:
```ts
export interface LinkRendererConfig {
  enabled: boolean;
  styleWikiLinks: boolean;
  styleSemanticLinks: boolean;
  wikiLinkColor: string;       // default: 'var(--emd-accent)'
  semanticLinkBadgeBg: string; // default: 'var(--emd-accent)'
}
```

With a `DEFAULT_LINK_RENDERER_CONFIG` constant. Add `linkRenderer: LinkRendererConfig` to `LiveMdConfig`.

### 2. wiki-link.ts — Wiki-Link Style Decorator

Create `sdk/react-emd/src/live-md/wiki-link.ts` with:

```ts
export function buildWikiLinkDecorations(
  tree: Tree,
  docText: string,
  config: LinkRendererConfig
): Range<Decoration>[]
```

Logic:
1. If config disabled, return `[]`
2. Scan `docText` for `[[...]]` patterns using regex (find all, with positions)
3. For each match, check that it doesn't fall within a FencedCode or HTMLBlock node (use `tree.resolve(from)` to check if the ancestor chain includes those types — or use the simpler approach: iterate tree nodes to build a set of "excluded ranges" from FencedCode/HTMLBlock)
4. For valid matches, apply `Decoration.mark()` with style:
   - `color: config.wikiLinkColor`
   - `textDecoration: 'underline'`
   - `textDecorationStyle: 'dotted'` (dotted underline for internal links)
   - `cursor: 'pointer'`
5. Apply the mark to the full `[[target]]` range (the brackets will be hidden by Fa1's LinkMark handler if they match — but since `[[` is not a standard LinkMark, Fa1 won't hide them automatically. You may need to ALSO add a `Decoration.replace({})` for the `[[` and `]]` characters specifically.)

**Important:** Fa1-SyntaxHider's `LinkMark` mapping only covers the standard `[` and `](` brackets. Wiki-link brackets `[[` and `]]` are NOT handled by Fa1. Fa3 should therefore:
- Apply `Decoration.replace({})` to hide the opening `[[` (2 chars) and closing `]]` (2 chars)
- Apply `Decoration.mark()` to the visible target text between them

### 3. semantic-link.ts — Semantic Link Badge Widget + Style

Create `sdk/react-emd/src/live-md/semantic-link.ts` with:

```ts
export function buildSemanticLinkDecorations(
  tree: Tree,
  docText: string,
  config: LinkRendererConfig
): Range<Decoration>[]
```

Logic:
1. If config disabled, return `[]`
2. Scan `docText` for lines matching `→ [a-zA-Z][a-zA-Z0-9-]*: ` pattern
3. For each match, verify it's not inside FencedCode/HTMLBlock
4. Parse the relation name (e.g., `depends`, `blocks`, `implements`) and target path
5. Create TWO decorations:
   a. `Decoration.replace({})` for the `→ ` prefix (3 chars: arrow + space), so the arrow is hidden
   b. `Decoration.mark()` for the relation name part with badge-like styling:
      - `backgroundColor: config.semanticLinkBadgeBg`
      - `color: #ffffff`
      - `borderRadius: '3px'`
      - `padding: '0 4px'`
      - `fontSize: '0.85em'`
      - `fontWeight: '600'`
   c. `Decoration.mark()` for the target path part with link styling:
      - `color: 'var(--emd-accent)'`
      - `textDecoration: 'underline'`
6. Skip `→` inside standard Link text — only match `→` at the start of a semantic link line

**Relation color mapping** (map relation name → badge color):
```ts
const RELATION_COLORS: Record<string, string> = {
```

### 4. link-renderer.ts — Unified Builder

Create `sdk/react-emd/src/live-md/link-renderer.ts` as the main builder function that delegates to wiki-link.ts and semantic-link.ts:

```ts
export function buildLinkRendererDecorations(
  tree: Tree,
  _ast: EmdDocument | null,
  config: LiveMdConfig,
  docText: string
): Range<Decoration>[]
```

This is the function that gets registered in the BUILDERS array. It calls both sub-builders and merges results.

### 5. ViewPlugin update

In `view-plugin.ts`, update the `BUILDERS` array and the `rebuildDecorations` method:
1. Add `(tree, _ast, config) => buildLinkRendererDecorations(tree, _ast, config, state.doc.toString())` as the third builder
2. Update `rebuildDecorations` to pass `state` to the builder call, or update the `DecorationBuilder` type to accept the document text

**Alternative simpler approach:** Pass `state` (or just `state.doc.toString()`) as an additional parameter in the builder loop. Update the DecorationBuilder type:

```ts
export type DecorationBuilder = (
  tree: Tree,
  ast: EmdDocument | null,
  config: LiveMdConfig,
  state: EditorState
) => Range<Decoration>[];
```

Then update all existing builders to accept the 4th parameter (unused).
