## What This Is

The `emd` crate compiled to WebAssembly via `wasm-pack` for browser and npm consumption. This is the bridge that makes EMD work in the Visual Interpreter's web-based UI, in any TypeScript/JavaScript project via npm, and in the standalone web version at `emd.dev`.

The WASM target is NOT a separate codebase. It is the same `emd` crate, compiled with `--target wasm32-unknown-unknown`, with JavaScript/TypeScript bindings generated by `wasm-bindgen`. The same parser, validator, and context loader that run natively on desktop run identically in the browser. The only difference is that file system operations (reading `.emd` files) go through JavaScript callbacks instead of `std::fs`.

## Why It Matters

Without the WASM target, the Visual Interpreter cannot parse `.emd` files in the browser. Every keystroke in the web-based editor would require a server round-trip for parsing — unacceptable latency. The WASM parser runs locally in the browser at near-native speed, enabling the 50ms debounced re-parse that keeps the AST in sync with the editor.

The WASM target is also what makes `@everthink/interpreter` possible as an npm package. A TypeScript developer can `npm install` the interpreter and use `<emd-editor>` in their React/Next.js/Vue app. The WASM parser is loaded transparently — the developer doesn't think about Rust or WASM, they just import a component.

## Architecture

The WASM build produces:
- `emd_bg.wasm` — the compiled Rust code (~383KB gzipped, 1.1MB uncompressed)
- `emd.js` — JavaScript bindings generated by wasm-bindgen (ESM, `--target web`)
- `emd.d.ts` — TypeScript type definitions
- `index.js` — npm package entry point (wraps async init + sync calls)
- `index.d.ts` — Extended TypeScript types with convenience API

Build command: `wasm-pack build --target web`

Cargo.toml release profile:
```toml
[profile.release]
opt-level = "z"  # maximize size optimization over speed
lto = true        # link-time optimization
codegen-units = 1 # single codegen unit for better LTO
strip = true      # strip symbols
```

## File System Bridge

The `emd` crate uses `std::fs` for file operations. In WASM, there is no filesystem. The solution is a virtual filesystem: the JavaScript host provides file content as strings, and the WASM module operates on those strings. The `EmdIndex` is built from files provided by the storage adapter.

The WASM `EmdIndex::build_virtual(files: Vec<(PathBuf, String)>)` takes a list of file paths and their contents. The rest of the pipeline (parsing, validation, context loading) operates on these in-memory files identically to native mode.

## Performance

WASM performance is 80-95% of native. The 500-section file that parses in 5ms natively parses in 6-8ms in WASM.

The `.wasm` file is ~383KB gzipped (1.1MB uncompressed). Size optimization applied: `opt-level="z"`, LTO, single codegen-unit, strip. wasm-opt was attempted but the cached binary (v117) requires `--enable-bulk-memory --enable-nontrapping-float-to-int` flags which are not passed by wasm-pack v0.14.0. The target of <200KB gzipped remains aspirational — reaching it requires replacing pulldown-cmark with a custom parser and moving to no_std.

WASM instantiation takes ~10ms (initSync path). First parse after init is ~10ms, subsequent parses are 5-8ms.

## npm Package

`@everthink/emd` publishes to npm with:
- `main`: `index.js` (convenience wrapper)
- `types`: `index.d.ts`
- `files`: `emd_bg.wasm`, `emd.js`, `emd.d.ts`, `index.js`, `index.d.ts`
- `sideEffects: ["./snippets/*"]`

The package exports:
- `parse(source: string, opts?): Promise<EmdDocument>` — parse EMD text, auto-inits WASM
- `serialize(doc: EmdDocument | string, opts?): Promise<string>` — serialize back to markdown
- `validate(doc, files, opts?): Promise<EmdDiagnostic[]>` — validate with virtual files
- `validateDirect(doc, files, opts?): Promise<EmdDiagnostic[]>` — JsValue-based validation
- `get_version(): string` — crate version
- `initSync(module): InitOutput` — synchronous init from pre-loaded WASM buffer

## Integration With Other Features

**Visual Interpreter**: The interpreter imports `@everthink/emd` for all parsing. The WASM module runs in the browser or Tauri WebView.

**npm Package (RF7)**: `@everthink/interpreter` depends on `@everthink/emd` for the WASM parser.

**Standalone Web**: The `emd.dev` website loads the WASM parser via CDN or bundled JS.

**TypeScript Compiler**: The TS compiler is a pure-TypeScript alternative to the WASM parser. It does NOT use the WASM target — it implements the parser in TypeScript directly.

## Known Limitations

- No multithreading in WASM (wasm-bindgen Rayon support is experimental)
- Virtual filesystem means all files must be loaded into memory before indexing (max ~50MB for a large project)
- WASM module cannot access the real filesystem — host must provide file content
- Streaming WASM compilation (Response.instantiateStreaming) requires proper MIME type on server

## V2 Plans
